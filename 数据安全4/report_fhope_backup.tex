\section{实验内容}

本次实验主题为密文查询，重点复现实验指导书 7.3.3 节中的频率隐藏顺序保持加密（Frequency-Hiding Order-Preserving Encryption，FH-OPE）方案。顺序保持加密（Order-Preserving Encryption，OPE）能够使数据库在不解密数据的情况下根据密文或编码执行范围查询，但普通 OPE 容易泄露明文顺序和重复值频率。FH-OPE 通过随机化密文和重复值随机插入位置，使相同明文对应不同密文和不同编码，从而缓解频率泄露问题\cite{boldyreva2009ope,kerschbaum2015fhope}。

本实验完成的主要工作如下：

\begin{enumerate}[label=\arabic*.]
    \item 在 WSL Ubuntu 环境中安装 MySQL、MySQL 开发头文件、C++ 编译工具和 Python 依赖，完成 FH-OPE 运行环境搭建。
    \item 根据指导书实现编码树结构，包括内部结点、叶子结点、编码分配、重编码和结点分裂。
    \item 将 FH-OPE 服务端逻辑封装为 MySQL UDF，注册 \code{FHInsert}、\code{FHSearch}、\code{FHUpdate}、\code{FHStart} 和 \code{FHEnd} 等函数。
    \item 编写并完善 Python 客户端 \code{client.py}，实现随机 AES 加密、插入、范围查询和重复插入测试。
    \item 多次插入相同明文 \code{apple}，观察编码区间压缩、编码更新、重编码和叶子结点分裂现象。
\end{enumerate}

\section{实验原理}

\subsection{OPE 与 FH-OPE}

OPE 的基本目标是在密文或编码上保留明文大小关系。若明文 $m_1<m_2$，则对应编码满足：

\[
    code(m_1)<code(m_2)
\]

因此数据库可以直接基于编码列执行范围查询：

\[
    code(l) \leq encoding < code(r)
\]

但普通 OPE 会泄露明文的全序关系，并且相同明文若对应相同密文或相同编码，将直接暴露频率分布。FH-OPE 的改进点在于：相同明文多次出现时不固定映射到同一个编码，而是在该明文对应的排序区间内选择不同插入位置；同时客户端对明文使用随机加密，使相同明文得到不同密文。这样服务器只能看到有序编码和随机密文，难以直接根据重复密文统计明文频率。

\subsection{编码树结构}

实验中服务端维护一棵编码树，结构类似 B+ 树。内部结点用于根据排名位置选择子树，叶子结点保存密文和编码。关键数据结构见表 \ref{tab:tree}。

\begin{table}[H]
    \centering
    \caption{FH-OPE 编码树关键结构}
    \label{tab:tree}
    \renewcommand{\arraystretch}{1.25}
    \begin{tabularx}{0.92\textwidth}{>{\bfseries}p{3cm}X}
        \toprule
        结构或函数 & 功能 \\
        \midrule
        \code{InternalNode} & 保存子结点指针和各子树记录数，根据全局位置定位插入路径。 \\
        \code{LeafNode} & 保存密文数组 \code{cipher}、编码数组 \code{encoding} 和叶子兄弟指针。 \\
        \code{Encode(pos)} & 在相邻编码之间分配新编码；若无可用空间则触发重编码。 \\
        \code{Recode} & 扩大更新区间并重新均匀分配编码，同时记录需要同步更新的密文。 \\
        \code{rebalance} & 当结点元素数达到阈值 \code{M=128} 时分裂结点。 \\
        \bottomrule
    \end{tabularx}
\end{table}

设插入位置左右边界编码分别为 $L$ 和 $R$。若 $R-L\geq 2$，则可直接选择中间值：

\[
    code = R-\left\lfloor\frac{R-L}{2}\right\rfloor
\]

若 $R-L<2$，表示当前区间内已经没有整数编码可用，需要执行 \code{Recode}。重编码会选取一个或多个相邻叶子结点构成更新区间 \([start\_update,end\_update)\)，将其中元素按当前顺序重新均匀分配编码。

\subsection{数据库同步机制}

实验中的 \code{pro_insert} 存储过程负责插入密文和同步编码。当 \code{FHInsert} 返回非 0 编码时，说明未触发重编码，直接插入即可；当返回 0 时，说明服务端编码树发生了编码更新，需要调用 \code{FHUpdate} 更新数据库表中受影响的记录。

\begin{lstlisting}[language=SQL,caption={pro_insert 中的编码同步逻辑}]
SET i = FHInsert(pos, ct);
INSERT INTO example(encoding, ciphertext) VALUES (i, ct);

IF i = 0 THEN
    UPDATE example
    SET encoding = FHUpdate(ciphertext)
    WHERE (encoding >= FHStart() AND encoding < FHEnd())
       OR (encoding = 0);
END IF;
\end{lstlisting}

\section{实验总结与反思}

本次实验完成了 FH-OPE 方案从服务端到客户端的端到端复现。实验中搭建了 WSL Ubuntu、MySQL、C++ UDF 和 Python 虚拟环境，实现了密文插入、范围查询、重复插入和编码树状态观察。基础 demo 证明了数据库可以基于编码列完成密文范围查询；重复插入实验则直观展示了编码空间被压缩后触发重编码，以及叶子结点达到阈值后发生分裂的过程。

实验过程中解决的主要问题包括：

\begin{enumerate}[label=\arabic*.]
    \item 指导书中存在包名和库名不一致的问题，例如 Python 包应为 \code{pymysql}，动态库统一为 \code{libfhope.so}。
    \item MySQL 8 默认认证方式需要 PyMySQL 配合 \code{cryptography} 使用，否则客户端连接会报错。
    \item MySQL UDF 必须复制到 \code{mysql_config --plugindir} 指定的插件目录，并通过 \code{CREATE FUNCTION ... SONAME} 注册。
    \item 编码树保存在 MySQL 进程内存中，实验时需要通过 \code{FHReset()} 和 \code{TRUNCATE TABLE example} 保持内存树与数据库表一致。
\end{enumerate}

从安全性角度看，FH-OPE 仍然会泄露明文之间的相对顺序，因此不能达到普通随机加密的语义安全强度。但它通过随机密文和重复值分散编码位置，降低了相同明文重复出现时的频率泄露。在需要支持高效范围查询的密文数据库场景中，FH-OPE 体现了查询功能与泄露控制之间的折中。

本实验也暴露出一些工程局限：极端插入策略下重编码会频繁发生，数据库更新开销较大；编码 0 兼作合法值和重编码信号，语义不够清晰；编码树缺少持久化机制，MySQL 重启后需要重新初始化。后续若要改进，可将重编码状态与编码值分离，引入持久化树结构，并进一步评估不同插入策略下的更新代价。
